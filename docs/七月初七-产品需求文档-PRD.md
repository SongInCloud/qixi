## 1. 项目概述

### 1.1 项目背景

作者希望在七夕之际，为特定的人（"她"）制作一份私人数字礼物。项目以中国传统七夕文化中的"女儿节""乞巧""织女""星河""星辰""祈愿"为核心意象，将网站设计成一次发生在七夕夜晚的短篇互动体验，最终打开一封专门写给她的信。

项目为单人、限时（12 小时）开发项目，由 AI 辅助开发完成，需要在有限时间内保证"完整体验链路优先于单个页面的极致复杂度"。

### 1.2 项目目标

- 打造一个完成度高、视觉精致、情绪克制的私人数字礼物网站。
- 让接收者（她）在 5～10 分钟内完成一次完整的夜间互动体验。
- 所有私人内容（回忆、女儿节卡片、信件）均可通过本地 Mock 数据独立维护，无需修改组件代码。
- 在 12 小时内交付一个可在 PC 与移动端正常运行的 MVP。

### 1.3 成功标准（产品层面）

用户完成网站后，应产生以下感受：

> 原来今天是女儿节。原来七夕还有这样的含义。原来你记得这么多关于我的事情。原来这些回忆都被藏在了星星里。原来你还让我自己许了一个愿望。最后还有一封信。

最终情绪不是"这个网站功能好多"，而是：

> **"你真的花时间为我做了这个东西。"**

## 2. 产品定位

### 2.1 产品定位

网站不是：

- 七夕宣传页
- 情侣相册
- 年度总结
- 传统文化介绍网站

而是：

> **一场发生在七夕夜里的私人数字礼物。**

用户应该感觉自己是在"夜晚中慢慢发现一些东西"，而不是不停点击网页。

### 2.2 核心概念

网站以一次完整的夜间体验构成：入夜 → 女儿节 → 星河 → 乞巧 → 七夕笺，最终打开一封写给她的信。

### 2.3 情绪关键词

整体情绪：

- 安静、温柔、浪漫、克制
- 东方、夏夜、星河
- 私人、仪式感、微微神秘

需要避免：

- 俗套情侣风、大面积红色、心形元素泛滥、玫瑰
- 情人节宣传页风格、商业营销风格
- 过度古风、过度复杂的国潮视觉、大量文字堆叠

## 3. 目标用户与使用场景

### 3.1 目标用户

唯一目标用户：

> 收到这个网站链接的她。

### 3.2 使用场景

- 场景一（PC）：她在电脑浏览器中打开链接，在安静的夜晚完成体验。
- 场景二（移动端）：她在手机上打开链接，在碎片时间或睡前完成体验。

### 3.3 明确不做（Out of Scope）

本产品不考虑以下内容：

- 用户注册、登录、多用户、权限体系
- 后台管理、CMS、数据统计
- SEO、分享系统
- 后端服务、数据库、在线上传
- 评论、社交功能
- 音乐系统（第一版默认不强制加入背景音乐）

## 4. 产品范围

### 4.1 本期范围（MVP）

- 五个完整章节：入夜、女儿节、星河、乞巧、七夕笺。
- 章节间的全屏切换动画。
- 背景星空（Canvas 或 CSS + 少量 DOM）。
- 记忆星星与回忆内容展示（数据来自本地 Mock）。
- 图片展示与 Lightbox 图片查看器。
- 乞巧愿望选择与自定义愿望输入、愿望入星河动画。
- 七夕笺信件阅读。
- PC 与移动端响应式适配。

### 4.2 后续可选范围（P1）

- 星星轻微闪烁、云层移动、月亮光晕、页面粒子。
- 卡片高级转场、图片平滑缩放、更丰富的背景纹理、小型彩蛋。
- 右下角静音/播放按钮（背景音乐，优先级最低）。

### 4.3 明确放弃范围（P2）

- 音乐、3D、WebGL、Three.js。
- 后端、数据库、登录、分享系统、CMS、管理后台、在线上传、数据统计。

### 5.1 信息架构

## 6. 功能需求

### 6.1 全局导航与章节切换

#### REQ-NAV-01：轻量章节提示

- 不需要传统 Header、导航栏、Logo、菜单或大量按钮。
- 可在页面右上角提供非常轻量的章节提示：`01 / 05`，或品牌文字"七月初七"。

#### REQ-NAV-02：全屏章节切换

- 章节之间使用全屏 transition。
- 推荐流程：当前章节 opacity 1 → opacity 0 → 背景变化 → 下一章节 opacity 1。
- 切换持续时间：800ms～1200ms。

#### REQ-NAV-03：禁止新增非需求功能

- 开发过程中不得自行增加登录、分享、评论、音乐系统、后台、数据库、复杂设置、用户系统等未经需求确认的功能。

### 6.2 章节一：入夜

#### REQ-INTRO-01：页面目标

让用户从现实进入"七夕夜"，是网站的情绪入口。

#### REQ-INTRO-02：初始状态

- 页面打开后为全屏深色背景。
- 页面中心几乎没有内容。
- 星星非常少，月亮隐藏，银河隐藏。
- 等待约 0.5～1 秒后开始动画。

#### REQ-INTRO-03：入场动画流程

按以下顺序依次呈现：

```
深色背景 → 第一颗星出现 → 第二颗星出现 → 更多星星缓慢出现
→ 月亮淡入 → 银河淡入 → 文字出现
```

#### REQ-INTRO-04：文案

- 第一句："七月初七。"
- 第二句："古人说，今夜宜乞巧。"
- 第三句："今夜没有什么特别的事情。只是想借着这一轮月亮，送你一点东西。"
- 按钮："入夜"

#### REQ-INTRO-05：入夜按钮交互

- 点击"入夜"进入下一章节。
- 按钮不设计成普通网页 Button，建议采用文字按钮 + 下方细线，hover 时线条扩展，点击后淡出。

### 6.3 章节二：女儿节

#### REQ-DAUGHTER-01：页面目标

介绍七夕"女儿节"含义，自然转入"她"。不做传统文化科普，重点为"今天是你的节日"。

#### REQ-DAUGHTER-02：页面文案

- 标题："今日为女儿节。"
- 副标题："古时女子于七夕乞巧，祈愿聪慧、灵巧，也祈愿未来。"
- 承接语："而我想把今夜，留给你。"

#### REQ-DAUGHTER-03：内容卡片

- 设计 6～8 个可点击内容卡片（真实内容不足时最低 4 个）。
- 卡片内容由本地 Mock 数据（`src/mock/daughter.ts`）提供，禁止硬编码在组件中。
- 卡片类型可包括："我记得""我发现""我喜欢""你的小习惯""你的小脾气""你喜欢的东西""只有我知道的事情""你说过的话"。

#### REQ-DAUGHTER-04：卡片数据结构

```ts
interface DaughterCard {
  id: string
  title: string
  subtitle: string
  content: string
}
```

#### REQ-DAUGHTER-05：卡片交互

- 默认状态展示：标题、短句、装饰符号。
- 点击后：卡片扩大、背景模糊、内容展开、出现完整文字、出现关闭按钮。
- 不建议弹出传统 Modal，建议采用"卡片 → 全屏/居中展开"的形式。

### 6.4 章节三：星河（核心互动章节）

#### REQ-STARRIVER-01：页面目标

将共同经历变成夜空中的星星。

核心文案：

> 我把记得的事情，都藏进了星星里。

#### REQ-STARRIVER-02：星河视觉

- 全屏深蓝背景。
- 大量星星、银河、月亮、少量云层。
- 星星不能全部一样，需要存在：大星、小星、模糊星、闪烁星、重点星。

#### REQ-STARRIVER-03：记忆星星数据管理

- 所有回忆节点必须使用本地 Mock 数据管理，文件：`src/mock/memories.ts`。
- 后续只修改该文件即可增删节点、修改标题/日期/地点/文字/图片/星星位置，不得修改组件代码。

#### REQ-STARRIVER-04：记忆星星数据结构

```ts
export interface Memory {
  id: string
  title: string
  date?: string
  location?: string
  description: string
  image?: string
  images?: string[]
  category?: string
  position: {
    x: number
    y: number
  }
  size?: "small" | "medium" | "large"
  color?: "white" | "gold"
  featured?: boolean
}
```

#### REQ-STARRIVER-05：星星定位

- position 使用百分比，如 `{ x: 32, y: 44 }`。
- 渲染时 `left: ${position.x}%; top: ${position.y}%`，避免不同屏幕尺寸下完全失控。
- 移动端可选提供独立 position（`desktop` / `mobile` 双份）；若实现复杂，第一版可只使用统一百分比。

#### REQ-STARRIVER-06：点击星星展示回忆

点击星星后依次：

```
星星变亮 → 背景轻微变暗 → 出现记忆内容
```

记忆内容展示：日期、标题、地点、图片、文字描述。

#### REQ-STARRIVER-07：回忆内容卡片

- 结构：图片区 → 日期 → 标题 → 地点 → 文字描述。
- 风格：半透明深色、月白文字、暗金装饰；不使用明显卡片阴影；圆角不要过大。

#### REQ-STARRIVER-08：图片展示

- 节点存在图片时必须支持单张与多张。
- 单张图片直接展示。
- 多张图片支持：横向滑动、左右切换、点击图片放大、全屏查看。

#### REQ-STARRIVER-09：图片查看器（Lightbox）

- 打开后背景 `rgba(0,0,0,0.9)`，图片 `contain` 展示。
- 操作：上一张、下一张、关闭。
- 移动端：支持左右滑动切换、点击关闭。
- PC 端：支持左右按钮、ESC 关闭、点击背景关闭。

#### REQ-STARRIVER-10：PC 悬停交互

- 星星 hover：变亮、轻微放大、出现标题。

#### REQ-STARRIVER-11：移动端触摸交互

- 不依赖 hover，点击星星即可打开内容。

#### REQ-STARRIVER-12：背景星星与记忆星星分离

- 背景星星：随机生成，每颗透明度不同，少量闪烁，动画周期不同；可使用 Canvas 或 CSS + 少量 DOM。
- 记忆星星：必须使用独立 DOM 元素（需要点击、hover、active、定位、显示标题）。
- 星星数量建议 100～180，不超过该数量。

### 6.5 章节四：乞巧

#### REQ-QIQIAO-01：页面目标

让用户真正参与一次"七夕乞愿"，是网站的核心互动仪式。

#### REQ-QIQIAO-02：页面文案

- 标题："乞巧"
- 正文："古人于七夕乞巧。乞聪慧，乞巧思，乞美好。那么今夜，你想求什么？"

#### REQ-QIQIAO-03：愿望选项

提供六个选项：求安、求乐、求愿、求巧、求遇、自书。

#### REQ-QIQIAO-04：快捷愿望文案

| 选项 | 愿望文案 |
| --- | --- |
| 求安 | 愿你所行之处，都有安心。 |
| 求乐 | 愿你往后的日子，有很多值得开心的小事。 |
| 求愿 | 愿你所想之事，都有慢慢实现的机会。 |
| 求巧 | 愿你心有巧思，也有把喜欢的事情做好的能力。 |
| 求遇 | 愿你一路所遇，都是温柔。 |

#### REQ-QIQIAO-05：自定义愿望（自书）

- 点击"自书"出现输入界面。
- 引导语："今夜，你想向星辰许什么愿？"
- 输入框最大 100 字，支持中文，自动适配移动端。
- 不需要提交服务器。
- 提交按钮："放入星河"。
- 空内容不允许提交，提示："写下一点什么吧。"

#### REQ-QIQIAO-06：放入星河动画

点击"放入星河"后依次执行：

```
愿望文字轻微缩小 → 逐渐变成光点 → 向星空移动 → 进入银河 → 形成一颗新星
```

最后显示：

> 愿你所愿，都有星河听见。

### 6.6 章节五：七夕笺

#### REQ-LETTER-01：页面目标

网站的情绪终点，整个页面必须非常克制。

#### REQ-LETTER-02：页面视觉

- 背景：深蓝黑、非常少的星星、一轮月亮。
- 中心：一张"七夕笺"，可使用 CSS 制作，不要求真实纸张图片。

#### REQ-LETTER-03：信件内容

- 标题："七夕笺"
- 开头："展信安。"
- 中间内容由项目作者自己填写，不由 AI 自动生成。
- 信件内容由本地 Mock 数据（`src/mock/letter.ts`）提供。

#### REQ-LETTER-04：信件数据结构

```ts
export const letter = {
  title: "七夕笺",
  greeting: "展信安。",
  paragraphs: ["第一段", "第二段", "第三段"],
  ending: "七夕快乐。"
}
```

### 6.7 结束状态

#### REQ-ENDING-01：结束文案

信件阅读完成后依次显示：

> 七月初七。愿你岁岁欢愉。所愿皆有所成。

然后显示：

> **七夕快乐。**

最后只剩星河，安静结束。

#### REQ-ENDING-02：结束页无多余元素

- 不需要返回首页、分享按钮、登录、推荐、Footer、版权信息。

## 7. 视觉设计规范

### 7.1 整体视觉方向

采用**现代东方 × 夏夜星河**，不是传统古风网站。

视觉参考意象：深夜、月光、银河、宣纸、墨色、月白、暗金、少量朱砂。

### 7.2 色彩规范

| 颜色用途 | 色值 |
| --- | --- |
| 背景深色 | `#080A18` |
| 深蓝 | `#10162C` |
| 次级蓝 | `#18213D` |
| 月白（主文字） | `#E9E3D5` |
| 次级文字 | `#AAA495` |
| 暗金 | `#C9A86A` |
| 淡金 | `#E3C98B` |
| 朱砂（少量点缀） | `#B84A42` |
| 半透明白 | `rgba(255,255,255,0.6)` |

色彩使用约束：

- 不要大量使用纯白。
- 不要使用高饱和蓝色。
- 不要大面积使用红色。

### 7.3 字体规范

优先采用系统字体，避免字体文件导致部署问题。

标题字体：

```
"Noto Serif SC", "Source Han Serif SC", "Songti SC", serif
```

正文字体：

```
"Noto Sans SC", "PingFang SC", "Microsoft YaHei", sans-serif
```

标题采用宋体/明朝体类字体，正文保持现代可读性。

### 7.4 图片规范

- 支持格式：jpg、jpeg、png、webp；推荐优先 webp。
- 回忆图片建议最长边 1600～2400px，不建议直接使用 5000px 以上原图。
- 图片压缩要求：单张 < 1MB，理想 200KB～800KB。
- 所有图片通过 `/images/...` 路径引用，存于 `public/images/`。

## 8. 交互与动画规范

### 8.1 动画原则

所有动画遵循：**慢、轻、柔和**。

禁止：

- 快速弹跳、夸张缩放、大量粒子爆炸
- 游戏化 UI、过多旋转

### 8.2 动画参数

| 动画类型 | 参数 |
| --- | --- |
| Fade | 0.8～1.5 秒 |
| Transform | 轻微位移：`translateY(10px)` → `translateY(0)` |
| Scale | 控制在 `0.96 → 1` |
| Blur | 用于页面切换、卡片打开、图片打开 |

## 11. 非功能需求

### 11.1 响应式设计

必须支持：

- PC：1440×900、1920×1080。
- 手机：375×667、390×844、430×932。

移动端不是简单缩小 PC，必须调整：字体大小、星星位置、卡片宽度、图片比例、按钮尺寸、间距。

### 11.2 性能要求

- 首屏加载迅速，不出现明显卡顿，移动端正常运行。
- 图片懒加载。
- 不使用大型 UI 框架；不引入大型动画库（除非确实需要）。
- 若使用 Canvas，限制粒子数量。

### 11.3 无障碍与用户体验

- 文本对比度足够。
- 点击区域至少 40×40px，移动端按钮容易点击。
- 图片具有 alt。
- 输入框有 placeholder。
- ESC 可关闭图片查看器。
- 用户刷新页面不会出现 JS 错误。

### 11.4 异常处理

| 场景 | 处理方式 |
| --- | --- |
| 图片加载失败 | 显示"图片暂时无法抵达这里。"，不影响页面继续运行 |
| Mock 数据为空 | 星河页面显示"今夜星河很安静。"，但正常运行 |
| 用户没有输入愿望 | 不允许提交空内容，提示"写下一点什么吧。" |

### 11.5 音乐

第一版不强制加入背景音乐（浏览器自动播放限制、移动端体验不稳定、素材与开发成本）。

如后续有时间，可增加右下角静音/播放按钮，优先级最低。

## 14. 开发原则与约束

### 14.1 开发原则

1. **视觉优先**：这是数字礼物，视觉体验优先级高于代码复杂度。
2. **不要过度工程化**：不使用状态管理库、API 层、Repository、Service、数据库、后端；简单 Vue 状态即可。
3. **组件化但不过度**：合理拆分 Section / Component / Mock Data 即可。
4. **私人内容数据化**：个人内容全部放 `src/mock/`。
5. **图片路径统一**：所有图片放 `public/images/`。
6. **不擅自增加产品功能**：不得自行增加登录、分享、评论、音乐系统、后台、数据库、复杂设置、用户系统，除非明确要求。

### 14.2 AI 开发行为约束

1. 优先实现 P0。
2. 不得为了"高级感"引入复杂技术。
3. 不得随意更换技术栈。
4. 不得擅自引入后端或数据库。
5. 不得擅自增加大型 UI 框架。
6. 不得把私人内容硬编码到组件中。
7. 所有回忆内容必须来自 Mock 数据。
8. 图片必须支持本地路径，且必须支持图片查看。
9. 必须兼容移动端。
10. 如果某项功能超过 30 分钟开发成本，应优先考虑简化。
11. 如果功能不是 P0，不得影响核心流程。
12. 不要因为追求完美而拖延核心功能完成。

## 17. 最终原则

这个项目只有一个最高优先级：

> **不要做一个"功能很多的七夕网站"。**

而是：

> **在 12 小时内，做一个足够精致、足够私人、足够安静的七夕数字礼物。**

内容可以少，功能可以少，图片可以少。但**每一个出现的东西，都应该有意义。**
